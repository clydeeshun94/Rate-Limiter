# How to Go Green on GitHub — 30-Day Plan

## What Are GitHub Contributions?

GitHub tracks your contributions on a 365-day graph. Each day is one square. A day is "green" if you have **at least one contribution** in any UTC timezone during that day. Contributions include: commits, PRs merged, issues opened/closed, forks, stars, reviews, gist edits, and repository creation.

**Key insight:** GitHub counts by UTC day, not your local day. If you're in a US timezone, pushing code at 11 PM your time might land on the *next* UTC day. Plan accordingly.

## The Strategy

The fastest path to a green graph is **diversification across multiple repositories**. One commit per day in one repo = green. But one commit per day across 3 repos = three times the green squares and three times the contribution history.

## 30-Day Schedule

| Days | Activity | What to Do | Why |
|------|----------|------------|-----|
| 1–2 | **Setup** | Create GitHub account (if needed), set up git config, create portfolio repo, make first commit | Foundation — everything builds from here |
| 3–4 | **First badges** | Earn Quickdraw (open+close own issue in 5 min), YOLO (merge own PR without review) on your portfolio repo | Two badges in under 5 minutes |
| 5–7 | **Fork & PR** | Find a popular repo with "good first issue" labels, fork, fix, open PR. Repeat 2–3 times | Start Pull Shark badge, begin open-source contributions |
| 8–14 | **Project 1 ramp** | Implement Rate Limiter: commit algorithm implementations, tests, docs daily (multiple commits per day) | Core learning + consistent green days |
| 15–17 | **Profile polish** | Add profile README, pin 3 repos, create a project showcase | Earn Profile README badge, improve first impression |
| 18–21 | **Expand projects** | Start Project 2 (Load Balancer) scaffolding + commit Project 1 refinements | Multiple repos = multiple green sources |
| 22–25 | **More PRs** | Submit 3+ more PRs to different open-source repos | Push Pull Shark toward Bronze (16 PRs), work toward Open Sourcerer |
| 26–28 | **Star & sponsor** | Star 16 repos to trigger Starstruck, sponsor one dev via GitHub Sponsors | Earn Starstruck + Public Sponsor badges |
| 29–30 | **Sprint finish** | Bulk commits across all active repos, finalize docs, write READMEs | Solidify 30 green days minimum |

## Daily Commit Tactics (5 minutes)

1. **Fork a repo with "good first issue"** — fix a typo, improve docs, fix a small bug
2. **Open a PR** — write a clear title and description
3. **Your own repos** — make a trivial change (update a comment, add a note, touch a config) and merge
4. **Star repos** — starring counts as a contribution
5. **Open issues** — ask a question or report a bug on any public repo

## Automation (optional but powerful)

Set up a GitHub Action in one repo to auto-commit daily. This guarantees at least one green square per day even on busy days. Use a cron schedule (e.g., `0 6 * * *` for 6 AM UTC). You can find many templates by searching "GitHub streak maintainer."

## Pro Tips

- **Multiple repos are your friend.** Spread commits across 3–5 repos daily
- **Timezone matters.** UTC midnight is the boundary — check your offset
- **All contribution types count:** commits, PRs, issues, forks, stars, reviews, gists, repo creation
- **Forked repo commits count** only if you are the fork owner
- **Stars count** when you star a repo you don't own (1 star = 1 contribution for that day)
- **GitHub Actions runs** do NOT count toward contributions (they use a bot account)
- **PR reviews count** — reviewing someone else's PR adds a contribution

# 5 Easiest GitHub Badges to Earn

GitHub Profile Achievements (badges) appear on your profile page and signal your activity level. Here are the 5 I recommend targeting first:

### 1. Quickdraw ⚡
- **Difficulty:** Very Easy
- **How to earn:** Open any issue or PR on any repo (including your own), then close it within 5 minutes
- **Tiers:** None — one and done
- **Time to earn:** 2 minutes
- **Why first:** Literally just open and close. No code needed.

### 2. YOLO 🎲
- **Difficulty:** Easy
- **How to earn:** On a repo you own, open a PR and merge it without requesting any review
- **Tiers:** None — one and done
- **Time to earn:** 2 minutes
- **Why second:** Zero-risk, self-contained, instant badge

### 3. Public Sponsor 💖
- **Difficulty:** Easy
- **How to earn:** Go to GitHub Sponsors, sponsor any developer or organization publicly (even $1)
- **Tiers:** None — one and done
- **Time to earn:** 3 minutes
- **Why third:** Costs nothing but a click, adds credibility to your profile

### 4. Pull Shark 🔀
- **Difficulty:** Easy
- **How to earn:** Merge at least 2 pull requests (default tier). Bronze at 16, Silver at 128, Gold at 1024
- **Tiers:** Yes (4 tiers)
- **Time to earn:** A weekend of fixing good-first-issues, or a few days spread out
- **Why fourth:** This is the gateway badge to open source. Start now, keep grinding

### 5. Pair Extraordinaire 👥
- **Difficulty:** Easy
- **How to earn:** Co-author a commit in a merged PR using `Co-authored-by: Name <email>` in the commit message
- **Tiers:** Yes (4 tiers — Default at 1, Bronze at 10, Silver at 24, Gold at 48)
- **Time to earn:** One conversation with a friend or study buddy
- **Why fifth:** Requires one collaborator but the badge scales beautifully with tiers

# Philosophy: Master Builder, Not Brick Maker

The developer is not interested in the syntax details - AI can handle that. The focus is on understanding how the **systems** work in detail. Rather than becoming a master brick maker, the goal is to become a master builder who uses pre-made bricks effectively.

This approach is brilliant because it focuses on:
- **System architecture understanding**
- **Mechanisms and trade-offs**
- **Failure modes and recovery**
- **Performance characteristics**
- **Integration patterns**

The syntax is just implementation detail - the real value is in comprehending how these systems function at a deeper level.

# 1. Configurable Rate Limiting Engine

**Architecture:** Modular Monolith — pluggable algorithm modules, swappable storage layer, configurable policy engine. Single deployable unit, clean internal boundaries.

**Database:** No — in-memory is the primary implementation. Redis-backed is the distributed version. MongoDB is too slow for counters (~5ms vs Redis ~0.1ms).

**Tested in:** Toy Project 1 (Content & Media Platform) — API call limits, upload rate limits, comment posting limits. Also tested in Toy Project 2 (URL Shortener) — URL creation limits, API rate limits.

**What you're building:** A standalone rate-limiting service/library that can protect arbitrary APIs. The rate limiter should not be tied to Express routes. It should expose a reusable interface such as `rateLimiter.check(identity, policy)` and support interchangeable algorithms.

**Algorithms to implement:** Fixed Window; Sliding Window Counter; Sliding Window Log; Token Bucket; Leaky Bucket.

**What to investigate:** Burst behavior; sustained traffic; memory requirements; accuracy; computational cost; fairness; boundary problems; distributed implementation; latency; storage requirements.

**Storage implementations:** Start with in-memory storage, then implement Redis-backed storage. Compare local per-process limiting with distributed limiting across multiple application instances.

**Demonstrate understanding of:** Concurrency; atomicity; race conditions; TTL; distributed state; counters; time windows; burst control; backpressure; fairness; horizontal scaling; Redis atomic operations; distributed rate limiting; configuration-driven architecture.

**Brutal test:** Be able to explain why you would choose Token Bucket over Sliding Window, and why two reasonable rate-limit implementations can produce different results for identical traffic.

# 2. Load Balancer & Traffic Distribution System

**Architecture:** Layered — Controllers (HTTP/proxy handlers), Services (routing algorithms), Models (server state/health), Routes (proxy endpoints), Middleware (balancer auth/logging).

**Database:** No — server health and connection state is ephemeral. In-memory is correct; if the balancer restarts, it re-discovers servers.

**Tested in:** Toy Project 1 (Content & Media Platform) — distribute traffic across encoding servers, API servers, CDN edge nodes. Also Toy Project 2 (URL Shortener) — distribute analytics query servers across regions.

**What you're building:** A reverse proxy/load balancer that distributes requests across backend servers.

**Algorithms:** Round Robin; Weighted Round Robin; Random; Weighted Random; Least Connections; Weighted Least Connections; IP Hash / consistent hashing.

**Health management:** Health checks; unhealthy-server detection; recovery; server registration; server removal; connection tracking; configurable health-check intervals; failure thresholds.

**Failure behavior:** Investigate what happens when a server dies, becomes slow, returns errors, or when all servers are unhealthy.

**Demonstrate understanding of:** Reverse proxies; TCP/HTTP request forwarding; connection management; traffic distribution; health checks; failure detection; retries; timeouts; sticky sessions; horizontal scaling; consistent hashing; availability vs performance; fault tolerance; load distribution.

**Brutal test:** Kill servers while traffic is running. Make one deliberately slow and another return errors. Demonstrate how the architecture responds. If it only works when everything is healthy, it is a demo, not a serious load balancer.

# 3. Authentication & Session Infrastructure

**Architecture:** Hexagonal (Ports & Adapters) — auth domain logic (token validation, session creation, password hashing) as ports; Redis, DB, memory as adapters. Swap storage without touching core logic.

**Database:** Yes — sessions, refresh tokens, user accounts, password hashes need persistence. MongoDB fits document-style auth data well.

**Tested in:** Toy Project 1 (Content & Media Platform) — user registration, JWT for API access, session management. Also Toy Project 2 (URL Shortener) — API key auth, user accounts for analytics.

**What you're building:** An authentication infrastructure system rather than merely a login page. Support multiple authentication models and compare them.

**Authentication models:** Stateful sessions; JWT access/refresh token architecture; short-lived access tokens; refresh-token rotation; token families; reuse detection; revocation; logout; expiry.

**Storage:** Compare in-memory sessions, Redis sessions, and database sessions.

**Token transport and browser security:** Cookies; Authorization headers; HttpOnly; Secure; SameSite; CSRF; XSS implications.

**Security mechanisms:** Password hashing; password verification; account lockout/rate limiting; session invalidation; refresh-token invalidation; token reuse detection.

**Demonstrate understanding of:** Authentication vs authorization; stateful vs stateless authentication; cryptographic signing; token lifecycle; session management; browser security; CSRF; XSS; credential storage; revocation; distributed authentication.

**Brutal test:** Explain why JWT does not magically eliminate sessions, how a supposedly stateless JWT can be revoked, and why putting JWTs in localStorage is not automatically a good architecture.

# 4. Distributed Cache System

**Architecture:** Event-Driven — cache invalidation, stampede prevention, and write-behind sync produce and consume events. When data changes → event fires → cache invalidates → other instances update.

**Database:** Yes — cache entries need persistence for distributed/shared cache version. In-memory first; Redis/MongoDB for production.

**Tested in:** Toy Project 1 (Content & Media Platform) — video metadata, thumbnails, trending content. Also Toy Project 2 (URL Shortener) — URL→short code lookups, shared cache across instances.

**What you're building:** A caching layer between an application and its data source.

**Caching strategies:** Cache Aside; Read Through; Write Through; Write Behind; Write Around.

**Eviction algorithms:** LRU; LFU; FIFO; TTL-based expiration.

**Hard problems:** Cache invalidation; stale data; cache stampede; cache penetration; cache avalanche; hot keys; cache warming; negative caching.

**Distributed version:** Move from application-local memory caching to a shared Redis-backed cache and investigate consistency.

**Demonstrate understanding of:** Latency; memory; locality; eviction; TTL; consistency; invalidation; distributed caching; serialization; cache/database synchronization; read/write tradeoffs.

**Brutal test:** Deliberately make the cache stale. Create a cache stampede and a hot key. Kill Redis. Explain exactly what the application does in each situation.

# 5. Message Queue & Event Processing System

**Architecture:** Event-Driven (Core) — a message queue is the backbone of event-driven architecture. Producers, consumers, retry handlers, and dead-letter processors all communicate through events. This is the infrastructure other systems will use.

**Database:** Yes — messages in queues, dead-letter queues, and visibility timeouts need persistence. A crashed consumer must not lose unprocessed messages.

**Tested in:** Toy Project 1 (Content & Media Platform) — video transcoding pipeline (upload → transcode → thumbnails → ready), notification delivery. Also Toy Project 2 (URL Shortener) — click events (click → log → aggregate → report).

**What you're building:** A messaging/event infrastructure with producers, consumers, acknowledgements, retries, and failure recovery.

**Implement:** Producers; consumers; acknowledgements; retries; dead-letter queues; visibility timeouts; delayed messages; message priorities; consumer groups; concurrency controls.

**Delivery semantics:** Understand at-most-once, at-least-once, effectively-once, and why exactly-once processing is difficult.

**Failure scenarios:** Handle a consumer that processes a message and crashes before acknowledging it. Investigate idempotency and duplicate processing.

**Demonstrate understanding of:** Asynchronous processing; decoupling; event-driven architecture; backpressure; concurrency; acknowledgements; retries; idempotency; delivery guarantees; failure recovery; eventual consistency.

**Brutal test:** Make consumers crash randomly, make the network fail occasionally, and allow duplicate messages. The system should still converge to a correct result.

# 6. Distributed Job Scheduler

**Architecture:** Microservices — scheduler, worker pool, job registry, and heartbeat monitor are separate services with distinct lifecycles and scaling profiles. Workers scale independently from scheduler.

**Database:** Yes — jobs, schedules, worker registration, and heartbeats need persistence. If a scheduler crashes, jobs must survive and be reassigned.

**Tested in:** Toy Project 1 (Content & Media Platform) — scheduled analytics aggregation, expired content cleanup, thumbnail regeneration. Also Toy Project 2 (URL Shortener) — expired URL cleanup, click aggregation, analytics reports.

**What you're building:** A distributed job-processing system in which applications submit jobs to a scheduler and a worker pool executes them.

**Implement:** Delayed jobs; recurring jobs; priorities; retries; exponential backoff; job timeouts; cancellation; job status; worker registration; worker heartbeats.

**Hard problems:** Worker crashes; scheduler crashes; duplicate execution; orphaned jobs; leader election; leases; heartbeats; job ownership; idempotency.

**Demonstrate understanding of:** Distributed coordination; scheduling; leases; heartsets; worker pools; concurrency; retries; fault tolerance; distributed state; leader election; the practical limits of exactly-once execution.

**Brutal test:** Pull the plug on a worker halfway through a job. The scheduler must eventually determine that nobody owns the job anymore and recover appropriately.

# 7. Mini Distributed Database / Replicated Storage System

**Architecture:** Microservices — primary node, replicas, and shards are separate services with distinct roles. They communicate through replication logs and consensus protocols. Distributed state at the data layer.

**Database:** It IS the database — you're building your own storage engine with replication, consistency guarantees, and failover. MongoDB is not used here.

**Tested in:** Toy Project 1 (Content & Media Platform) — distributed video metadata storage, replication across regions. Also Toy Project 2 (URL Shortener) — distributed URL storage, failover-safe redirects.

**What you're building:** A deliberately simplified distributed storage system to understand replication and consistency. You are not trying to recreate PostgreSQL.

**Architecture:** Start with a primary and replica, then move to a primary with multiple replicas.

**Implement:** Writes; reads; replication; replication logs; replica health; replication lag; leader failure; replica promotion; recovery.

**Consistency models:** Strong consistency; eventual consistency; read-after-write consistency.

**Explore:** Leader/follower replication; write acknowledgement; quorum concepts; conflict scenarios; network partitions; split brain; failover; recovery.

**Demonstrate understanding of:** Replication; consistency; availability; partition tolerance; CAP theorem; quorum; leader election; replication lag; failover; distributed state; network partitions.

**Brutal test:** Simulate primary failure while replicas remain alive. Then simulate a network partition. Explain exactly what the system does and why.

# 8. Mini Rendering Engine

**What you're building:** A simplified UI rendering system to understand what frontend frameworks actually solve, rather than simply cloning React.

**Implement:** Transform a declarative component/tree representation into DOM, then implement updates.

**Explore:** Virtual DOM; reconciliation; diffing; DOM updates; component trees; state; rendering; batching.

**Demonstrate understanding of:** DOM; browser rendering; virtual DOM; reconciliation; diffing; component architecture; rendering costs; batching; state updates.

**Brutal test:** Render thousands of nodes and profile what actually costs time. Do not rely on assumptions about performance.

# 9. Client-Side Data / Cache Synchronization Engine

**What you're building:** A frontend data layer with a query cache, network layer, and synchronization behavior.

**Implement:** Request deduplication; caching; TTL; stale data; background refetching; retries; cancellation; optimistic updates; invalidation; pagination; infinite scrolling.

**Concurrency problem:** Handle out-of-order responses so an older response cannot accidentally overwrite newer state.

**Demonstrate understanding of:** HTTP caching; client-side caching; asynchronous state; race conditions; request cancellation; stale data; optimistic UI; synchronization; pagination; consistency.

**Brutal test:** Throttle the network, make requests resolve out of order, drop requests, reconnect, and verify that UI state remains correct.

# 10. Offline-First PWA & Synchronization Engine

**What you're building:** A frontend that remains useful when the network disappears, with local data and a synchronization engine.

**Implement:** Service Worker; Cache Storage; IndexedDB; offline reads; queued writes; synchronization; retry; conflict detection.

**Conflict resolution:** Investigate last-write-wins; timestamps; version numbers; optimistic concurrency; conflict resolution strategies.

**Demonstrate understanding of:** Browser storage; Service Workers; caching; offline architecture; synchronization; eventual consistency; conflict resolution; network failure; optimistic updates.

**Brutal test:** Use the application while offline, reconnect, and deliberately create conflicting changes from two clients. The system must make its conflict behavior understandable.

# 11. Virtualized Rendering Engine

**What you're building:** A system that can display extremely large datasets without rendering every item into the DOM.

**Implement:** Windowing; virtualization; dynamic row heights; scrolling calculations; overscan; recycling; viewport measurement.

**Investigate:** Why rendering hundreds of thousands or millions of DOM elements causes problems. Understand DOM memory, layout, paint, compositing, event handling, and garbage collection.

**Demonstrate understanding of:** Browser rendering pipeline; DOM performance; layout; paint; compositing; virtualization; memory; scroll performance; measurement.

**Brutal test:** Compare normal rendering and virtualization for 10k, 100k, and 1m items. Measure and explain the results.

# 12. Frontend State & Event Architecture

**What you're building:** A state-management/event system from scratch that explores different approaches to frontend state.

**Explore:** Local state; global state; derived state; immutable updates; subscriptions; selectors; middleware; event buses; pub/sub; undo/redo; state machines.

**Core question:** Understand the difference between state, events, and derived state, and how changes propagate through a component tree.

**Demonstrate understanding of:** State ownership; unidirectional data flow; subscriptions; event-driven architecture; immutability; derived state; selectors; state machines; event buses; update propagation.

**Brutal test:** Change one small piece of state in a large component tree and ensure that only what actually needs updating is updated.

# 13. Browser Networking & Real-Time Transport System

**What you're building:** A frontend networking layer that supports and compares HTTP, WebSocket, Server-Sent Events, and long polling.

**Implement:** Reconnect logic; exponential backoff; connection state; heartbeats; message ordering; duplicate-message handling; buffering; offline messages; subscription management.

**Streaming:** Investigate HTTP streaming, chunked responses, backpressure, buffering, and connection lifetime.

**Demonstrate understanding of:** HTTP; TCP connection behavior; WebSockets; SSE; long polling; streaming; reconnection; heartbeats; message ordering; network failure.

**Brutal test:** Disconnect the network repeatedly. The UI should represent connection states and recover without duplicating subscriptions or corrupting state.

# 14. Frontend Build / Module / Asset Pipeline

**What you're building:** A miniature frontend build system that transforms source modules into optimized browser assets.

**Implement/explore:** Module resolution; dependency graphs; bundling; code splitting; dynamic imports; tree shaking; asset hashing; source maps; minification; CSS processing; chunk generation.

**Dependency graph:** Represent how modules depend on one another, then turn that graph into browser-deliverable bundles.

**Investigate:** Why imports become downloadable/executable browser assets; why code splitting exists; why chunks are hashed; why tree shaking works sometimes but not always.

**Demonstrate understanding of:** JavaScript modules; dependency graphs; bundling; compilation/transformation; code splitting; lazy loading; tree shaking; browser loading; caching; source maps; asset optimization.

## Toy Projects for Practical Integration Testing

### Toy Project 1: Content & Media Platform

A backend service for a video/content platform (think YouTube or TikTok backend). This serves as the primary integration test bed.

**Why this over ecommerce:** E-commerce is overused and doesn't stress test all tools in interesting ways. A media platform is read-heavy (caching), write-heavy (uploads), async-heavy (transcoding), and has clear rate limiting needs — it exercises every tool more naturally.

**Which tools it tests:**
- **Rate Limiter** → API call limits per user, upload rate limits, comment posting limits
- **Load Balancer** → Distribute traffic across video encoding servers, API servers, CDN edge nodes
- **Auth** → User registration, JWT for API access, session management, refresh token rotation
- **Distributed Cache** → Video metadata, thumbnails, trending content, user profiles (massively read-heavy)
- **Message Queue** → Video transcoding pipeline (upload → transcode → generate thumbnails → ready), notification delivery
- **Job Scheduler** → Scheduled analytics aggregation, expired content cleanup, periodic thumbnail regeneration
- **Cross-Cutting** → Shared cache across multiple API instances, session replication across nodes

### Toy Project 2: URL Shortener with Analytics

A URL shortening service with real-time click analytics. Simpler than Toy Project 1 but exercises different patterns.

**Why this as a second project:** It tests all tools in a different context — read-heavy (URL lookups), event-driven (click tracking), and has different data shapes. Proves the tools aren't only good for one use case.

**Which tools it tests:**
- **Rate Limiter** → URL creation limits per user, API rate limits for shortening
- **Load Balancer** → Distribute analytics query servers across regions
- **Auth** → API key authentication for shortening, user accounts for analytics dashboards
- **Distributed Cache** → URL → short code lookups (every click hits the cache first), cache invalidation when URL expires
- **Message Queue** → Click events (click → log → aggregate → report), bulk analytics processing
- **Job Scheduler** → Expired URL cleanup, click aggregation jobs, link analytics reports
- **Distributed Cache** → Shared URL cache across instances, failover-safe URL redirects

### Shared Database: MongoDB

Both toy projects use MongoDB as their database. This is a throwaway database — simple MongoDB instance for realistic testing. When you understand what MongoDB hides, we'll explore other databases.

# The Portfolio Standard

**1. Implementation:** It works.

**2. Multiple strategies:** Where meaningful, implement competing approaches rather than only the easiest solution.

**3. Failure simulation:** Deliberately break the system: network failures, server failures, database failures, worker failures, duplicated requests, late requests, stale caches, and similar conditions.

**4. Measurements:** Measure latency, throughput, memory, CPU, error rate, cache hit ratio, requests per second, render time, DOM nodes, bundle size, and other relevant metrics instead of making performance claims from intuition.

**5. Engineering document:** Document the problem, why it exists, architecture, algorithms, implementation, alternatives, tradeoffs, failure modes, experiments, benchmarks, limitations, and what you learned.

# What This Portfolio Should Communicate

The goal is not to communicate: "Look at all the things I can code." The goal is to communicate: "Give me a systems problem. I understand the mechanisms underneath it, I know there are multiple ways to solve it, I understand the tradeoffs, and I can experimentally determine which approach is appropriate.

# Recommended Development Philosophy

Build these progressively from lower-level Go standard library and OS primitives first, then introduce abstractions such as Redis, MongoDB, Docker, and other infrastructure. The point is to understand what the abstractions are hiding rather than merely learning how to configure or use them.

For frontend projects (8–14), build from raw DOM, browser APIs, and vanilla JavaScript first, then introduce React, WebSockets, and other frameworks.
